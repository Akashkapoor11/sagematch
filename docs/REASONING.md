# End-to-end reasoning trace

This document walks through the bundled demo query **"I need a CRM for a 20-person sales team that integrates with Slack"** and shows what is deterministic, what is API-first, and what evidence reaches the final answer.

---

## Stage 1 — Data sanitisation (`backend/app/core/data_pipeline.py`)

Before queries run, the catalogue is converted into the canonical product model.

For the bundled demo catalogue, the current validation result is:

```json
{
  "rows_received": 39,
  "rows_accepted": 34,
  "rows_rejected": 2,
  "duplicates_removed": 3
}
```

The pipeline repairs case/alias inconsistencies, parses team-size ranges, splits list fields, normalizes URLs, removes URL-like deployment noise, detects duplicates, generates safe IDs, preserves unknown source columns in `extra_fields`, and records every repair/rejection in `DataQualityReport`.

The health score describes the quality of the **sanitized dataset that is retained**. Rejected rows and removed duplicates remain visible in the audit report rather than being counted as defects in data that was successfully discarded.

---

## Stage 2 — Requirement extraction (`query_understanding.py` + `llm.py`)

### 2a. API-first extraction

`LLMClient.understand()` is called first whenever an API is configured. The request includes the actual catalogue vocabularies so the model must return canonical values already known to the catalogue.

Expected shape:

```json
{
  "category": "CRM",
  "team_size": 20,
  "integrations": ["Slack"],
  "excluded_integrations": [],
  "features": [],
  "deployment": [],
  "pricing_tier": null,
  "confidence": 0.95
}
```

### 2b. Contract validation

An API response is accepted only when it remains inside the supplied vocabulary and preserves explicit query signals. For example, if the query explicitly says `CRM`, `Slack`, and `20 users`, an API response that omits one of those signals is rejected.

A rejected or failed API call immediately activates the deterministic parser. The parser is not run first and is not used to silently replace a valid API result.

### 2c. Probing

After requirements are known, SageMatch checks whether the request is sufficiently specified. For an ambiguous request such as **"I need software for my business"**, the probing stage asks the API first for high-impact questions. The deterministic information-gain planner is the fallback.

Questions are drawn from missing dimensions such as category, team size, integrations, deployment, pricing, and features. The planner uses catalogue variation/entropy and caps each round at three questions.

---

## Stage 3 — Constraint-aware ranking (`backend/app/core/ranker.py`)

Every product receives a grounded score using:

| Dimension | Weight |
|---|---:|
| Category | 27% |
| Integrations | 21% |
| Features | 16% |
| Team size | 15% |
| Deployment | 12% |
| Pricing | 5% |
| Semantic overlap | 4% |

Explicit category, team-size, integration, deployment, and exclusion requirements are represented as hard constraints. When at least three fully compliant products exist, the top three are selected only from the strict pool.

For the current demo query, the deterministic strict pool contains **5 CRM products**. The top three deterministic results are:

```text
1. SalesPilot   — 96.35%
2. FlowCRM      — 96.17%
3. DealFlow CRM — 95.83%
```

These scores are ranking signals, not organizer-supplied benchmarks.

### API reranking

If the LLM is configured, the API receives only the grounded candidate pool. It must return **every supplied candidate ID exactly once**. Unknown, duplicate, partial, or malformed orderings are rejected. Strict candidates are then placed ahead of relaxed fallbacks regardless of model ordering.

---

## Stage 4 — Grounded explanation (`backend/app/core/llm.py`)

The explainer receives only:

- the selected product,
- matched requirements,
- unmet requirements, and
- evidence generated by the ranker.

The API is called first. Its output is accepted only if every recommendation is covered and the text overlaps supplied evidence. Otherwise the deterministic explanation is retained.

Each evidence item carries the originating catalogue `source_row`, so a judge can trace the recommendation back to the input data.

The final UI exposes:

```text
Why it fits
Improve the fit
Decision evidence & score
Score breakdown
source row
```

This separation is deliberate: the catalogue and ranker are the source of truth; the LLM is a controlled reasoning and phrasing layer.

---

## Key invariants

1. **API first:** configured API is attempted before the deterministic fallback at every LLM-assisted stage.
2. **Fallback only on failure:** transport errors, invalid JSON, or contract violations trigger deterministic fallback.
3. **Catalogue is the source of truth:** the system cannot invent a product outside the sanitized catalogue.
4. **Hard constraints precede reranking:** the LLM can reorder a grounded pool but cannot weaken constraint precedence.
5. **Evidence before explanation:** explanations are generated from evidence that already exists in the ranker output.
6. **Provenance survives end-to-end:** recommendation evidence carries the original catalogue row number.
